# ACHEWIW · жанровые мастерские и библиотека источников — план исправлений

**25 ноября 2026 · статус: согласованный список недостатков и проектирование, БЕЗ реализации.**
**Не изменять активный конвейер, страницы или сервер по этому документу.** Не считать написанный план подтверждением функциональности. Доработки делать после ближайшего P0: контроля смысла/редактуры существующей рукописи.

## Фактическая проблема

В `app/static/index.html` поля «Атмосфера» и «Замысел / центральный конфликт» отображаются для technical, nonfiction, speech, хотя они придуманы для fiction. Рабочие тексты `workModes` и названия разделов в `app/static/app.js` уже различаются, и часть специфичных полей существует (sources, claims, duration_minutes, speaker_notes), но общая форма и генератор всё ещё требуют жанровой специализации на каждом шаге. Не нужно заменять реальную архитектуру ещё одним универсальным генератором.

## 1. Техническая, инженерная и научная литература (P1 после P0)

**Вместо атмосферы/конфликта:** техническая тема, границы предметной области, цель книги, аудитория и её стартовые знания, уровень сложности, тип материала (справочник, учебник, руководство, научно-популярное издание), используемые версии технологий и стандарты, допущения/исключения, наличие практических примеров.

**Генерация структуры:** тема → подразделы предметной области → разделы/главы → определения и необходимые предварительные знания → объяснения → схемы/формулы/примеры → проверка/ограничения → выводы и список подтверждённых источников. Автор может перестроить и утвердить главы до начала написания.

**Контроль качества:** согласованность терминов, размерностей, формул, версий стандартов, зависимостей разделов, реальность ссылок и DOI, отсутствие вымышленных доказательств; различие между источником, фактами и суждением LLM.

## 2. Нонфикшн, деловые, учебные и исследовательские книги (P1 после P0)

**Вместо атмосферы/центрального конфликта:** тема и предмет, главный вопрос, задача читателя, аудитория, метод исследования, точка зрения автора, проверяемые тезисы, ограничения источников и уровень доказательности.

**Генерация структуры:** вопрос → подтемы → тезисы → данные/кейсы/проверяемые аргументы → альтернативные объяснения и контраргументы → выводы. При необходимости автор выбирает тон изложения, но это не художественная «атмосфера».

**Контроль качества:** отделять проверенные факты от авторских оценок, не выдумывать исследования, даты, имена, цитаты и библиографию; обозначать пробелы доказательств.

## 3. Выступления, лекции и доклады (P1 после P0)

**Вместо атмосферы/центрального конфликта:** цель выступления, аудитория и контекст, главный тезис, предполагаемый эффект/действие слушателей, длительность, стиль подачи, формат, структура слайдов и устного выступления.

**Генерация структуры:** вступление → ключевые блоки и переходы → аргументы/демонстрации → резюме → финальный призыв или вопросы; минуты и целевой темп по блокам. Автор меняет текст и тайминг, включая диктовку.

**Контроль качества:** хронометраж, произносимость, связность переходов, соответствие аудитории, фактчекинг и отсутствие повторов.

## 4. Фантастика и художественная проза (сохранить)

Здесь нынешние поля «Атмосфера», «Замысел / центральный конфликт», «Твист», «Когда раскрыть», «Канон мира» уместны. Сохранить детальный каркас, режиссуру глав, граф причин/неразгаданных тайн, мягкую паузу, авторское вмешательство, существующую книгу и её редакции. Совершенствовать P0 семантических повторов, своевременность раскрытий и дифференцированные цели глав. **Не переносить художественные правила на технические, документальные или речевые тексты.**

## 5. Комиксы (запланировать, НЕ реализовывать сейчас)

Самостоятельного `work_type=comic` в подтверждённом текущем Studio нет. Подготовить будущую специализированную мастерскую: концепция/мир → авторский сценарий → сцены → сценарий кадров → страницы или вертикальные свайпы → пузыри/реплики → утверждение иллюстраций → вёрстка и выпуск. Учитывать последовательность персонажей/действий/объектов, стабильные визуальные референсы, короткие реплики, композицию кадра, контроль авторских прав и ручную приёмку.

Комикс — не «художественная книга со случайными картинками»; формат страницы, порядок кадров и работа с изображениями требуют отдельной модели данных. Включать только после базовой редакционной приёмки, без ломки уже действующей студии фантастики.

## Общая библиотека источников по тематике (спроектировать, НЕ добавлять загрузчик сейчас)

**Авторское предложение:** папка с собственными книгами, статьями, методичками и прочими разрешёнными материалами для отдельного произведения/темы, доступная модели при создании плана и текста. Не рассчитывать исключительно на «память LLM» или гарантированный поиск в интернете.

Принципиальная последовательность:
1. Отдельная управляемая библиотека проекта: загруженные книги/статьи/текстовые документы и локальные тематические папки с явным разрешением на индексирование; не использовать книги других проектов без согласия.
2. Извлечение текста, разметка заголовков и страниц/разделов, метаданные автора, названия, года, лицензии, происхождения файла и хеш; неизменный оригинал, версионирование индекса.
3. Индексация по фрагментам и структуре: SQLite FTS5 + векторный поиск (например, имеющийся `nomic-embed-text`) + связи графа между понятиями/фактами/доказательствами. Не вводить Hadoop и тяжёлые технологии без реальной потребности.
4. Тема → запросы к библиотеке → источники/выжимка → автор утверждает тематический план → генератор использует только релевантные цитаты/факты и общий контекст → редактор проверяет утверждения по источникам.
5. **Трассировка**: текстовый тезис ↔ загруженный документ ↔ точное место/страница/раздел ↔ статус проверки. При отсутствии источника писать «требует проверки», не придумывать DOI и библиографию.
6. Не отправлять файлы в облако без разрешения; учитывать чужие авторские права и разрешённое использование произведений; ограничения объёма/формата и очистку индекса проектировать отдельно.

Система может применять собственные знания модели, но хранить границу между проверяемым локальным источником, общеизвестным утверждением и предположением; источники не гарантируют отсутствие ошибок.

## Правильный порядок реализации (без торопливого расширения)

- **P0 СЕЙЧАС:** редактура и смысловой QA уже созданной книги: повторы, преждевременная разгадка, неоснованные детали, авторские изменения с версионированием и отдельной приёмкой; затем независимый DOCWORK для собственной внешней книги. Не генерировать тестовую книгу заново.
- **P1 ПОСЛЕ:** скрыть и корректно заменить неуместные художественные поля для technical/nonfiction/speech; сохранить обратную совместимость JSON/SQLite существующих проектов, проверить, что промпты/структура/QA также жанрово-специализированы.
- **P1 СЛЕДОМ:** спроектировать и реализовать библиотеку тематических источников с безопасным импортом, provenance и RAG; сначала маленький проверяемый пример технической книги.
- **P2 ПОЗЖЕ:** мастерская комиксов отдельным независимым сценарием без ущерба книжным мастерским.
- **ПОСЛЕ ОСНОВНОГО КОНВЕЙЕРА:** Верфь и прочие будущие направления по отдельной спецификации.
