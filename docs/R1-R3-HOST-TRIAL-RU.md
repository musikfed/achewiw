# ACHEWIW: запуск R1–R3 на испытательном Huananzhi

**Дата:** 23.11.2026. **PR:** [#26](https://github.com/musikfed/achewiw/pull/26).  
**Проверенный исходник:** ветка `fix/r3-docwork-durable-sessions-20261123`.  
**Рабочий сервер:** `/1tbdisk/achewiw`, Docker Compose `achewiw`, только собственный контейнер `achewiw-studio`, порт 7080.  

## Что делает сценарий

- Перед изменениями проверяет корень репозитория и его `origin`, чистоту Git, доступ к Docker и не менее 4 GiB на системном разделе (ранее было 93% занято).
- Забирает ветку R3 из GitHub, сохраняет в диагностике исходную ветку и SHA, переключает **только исходный код ACHEWIW**, без `git reset`, `clean`, `prune` или действий с другими репозиториями.
- Через уже существующий `scripts/achewiw-control.sh rebuild` пересобирает только `achewiw-studio`. Скрипт управления проверяет Compose-метки и владельца каталога, не затрагивает Ollama, AI Draftsman или ComfyUI.
- После старта внутри того же контейнера выполняет `scripts/r1-r3-host-smoke.py`: синтетический PDF с изображением и двумя колонками → DOCX (R1); синтетическая иллюстрированная книга DOCX/PDF и пропавший PNG (R2); тестовый черновик SQLite через HTTP с оригиналом, редактированием, HTTP 409 и версионированием (R3).
- **Только синтетический R3-черновик** после успешного создания явно закрывает по своему токену; действующие рукописи и SQLite-записи проектов не удаляет.
- Создаёт маленький *санитизированный* Markdown-отчёт. При наличии уже авторизованного `gh` автоматически прикрепляет его комментарием к PR №26. Иначе печатает отчёт в терминал, откуда его можно отправить в ChatGPT для записи в PR через подключённый GitHub.
- Полные технические логи оставляет **локально в `/tmp/achewiw-r123-qa.*/`** (600/700), их в публичный GitHub не публикует: там могут быть служебные детали хоста. Загрузка полных `docker logs` и секретов запрещена.

## Команды (в терминале Huananzhi, от пользователя с доступом к Docker)

```bash
cd /1tbdisk/achewiw || exit 1

git fetch --no-tags origin \
  '+refs/heads/fix/r3-docwork-durable-sessions-20261123:refs/remotes/origin/fix/r3-docwork-durable-sessions-20261123'

git show refs/remotes/origin/fix/r3-docwork-durable-sessions-20261123:scripts/r1-r3-host-run.sh \
  > /tmp/achewiw-r123-host-run.sh

bash -n /tmp/achewiw-r123-host-run.sh &&
bash /tmp/achewiw-r123-host-run.sh
```

Перед выполнением можно прочитать `/tmp/achewiw-r123-host-run.sh`; код находится в [GitHub](https://github.com/musikfed/achewiw/blob/fix/r3-docwork-durable-sessions-20261123/scripts/r1-r3-host-run.sh).

**Ожидаемые признаки:** `HOST SMOKE PASS`, `R1 PDF raster preserved`, `R2 PDF figure and caption share page`, `R3 GET after F5 restores revision and state`, `R3 stale second-tab revision rejected`; обычное открытие `http://192.168.0.100:7080/docwork/`.

## После автоматического теста — ручная проверка F5 в браузере

1. Открыть `/docwork/` по LAN/VPN, выбрать небольшой **синтетический DOCX**, «Проверить структуру». Проверить появление «Исходный файл сохранён на сервере».
2. Изменить стиль, текст обычного абзаца и название файла. Дождаться статуса «Черновик сохранён». Нажать **F5** в **той же вкладке**.
3. Ожидается восстановление источника, стиля, подготовленной правки, текста открытого редактора и истории. Проверить экспорт DOCX.
4. **Дублировать вкладку браузера** с сохранённой сессией, изменить исходную вкладку, затем попытаться сохранить старую редакцию во второй вкладке. Ожидается **HTTP 409**, а не потеря первой правки. Если браузер не копирует sessionStorage в новую вкладку, достаточно API-теста и отдельно зафиксировать это ограничение.
5. Проверить в PDF, что изображение и подпись находятся вместе. Открыть DOCX в MS Word/LibreOffice для реальной визуальной приёмки. Только после этого можно перевести ручной пункт D13 из `not_tested`.

## Ручной откат к прежнему коду (только при необходимости)

**Не удалять и не сбрасывать `data/`.** В отчёте есть прежняя ветка и полный SHA. Чтобы вернуть **именно предыдущую версию кода** и пересобрать только ACHEWIW:

```bash
cd /1tbdisk/achewiw || exit 1
git status --short                # убедиться, что нет новых правок
git switch --detach ПРЕЖНИЙ_SHA  # вставить SHA из санитизированного отчёта
bash scripts/achewiw-control.sh rebuild
```

Ранее созданные R3-таблицы остаются в SQLite и не удаляются; старая версия кода просто не использует их. Это **откат исполняемого кода, не откат данных**. Не выполняется автоматически.

## R4 — что понадобится

Для начала R4 **не требуются** новые LLM, ComfyUI, CUDA, отдельные коммерческие плагины или большие скачивания: текущие DOCX/PDF-библиотеки и LibreOffice уже покрывают базовые операции вёрстки. Понадобятся легально доступные и актуальные тексты конкретных стандартов с поправками, эталонные документы и точные критерии проверки. Следует начать с: ГОСТ Р 7.0.100-2018 (описание), ГОСТ Р 7.0.5-2008 (ссылки), ГОСТ Р 7.0.108-2022 (электронные ресурсы), а для отчётов НИР — ГОСТ 7.32-2017. Не загружать полные тексты стандартов в публичный GitHub без проверки условий распространения.

**Ограничение:** нет прямого SSH-доступа ChatGPT к Huananzhi. Подготовленные команды выполняются человеком в терминале, после чего санитизированный отчёт попадает в PR через `gh` или через ChatGPT. Нельзя утверждать, что хостовое развёртывание уже было произведено на основании CI.
