# ACHEWIW — методика испытаний DOCWORK и Vision (R3.1–R3.8)

**Дата фиксации:** 24 ноября 2026 года. **Цель файла:** сохранить мотивы, ход разработки и смысл каждого уровня проверок, чтобы будущие версии не превращались в бесконечный цикл «новая кнопка → старые 27 PASS → пересборка».

**Основа фактов:** исходные тесты в этом репозитории и журналы испытаний, переданные владельцем Huananzhi. Не приравнивать сообщение `PASS` к доказанному качеству распознавания или ручной работе интерфейса.

## 1. Зачем вообще понадобились тесты

ACHEWIW — редактор книги и иллюстраций на том же хосте, что локальная Ollama и другие приложения. Исправление одной функции не должно разрушать другую: исходный DOCX необходимо сохранять побайтно, чужие рукописи и проекты не менять, токены черновиков не раскрывать, GPU не занимать без разрешения. Поэтому проводятся **несколько разных типов проверок**:

- **Синтаксис (fast gate):** Python `py_compile` и Node `--check` ловят ошибки загрузки файлов; не гарантируют корректность исполнения функций.
- **Unit (offline):** данные создаются тестом; проверяются предельные случаи, недопустимые связи и форматы. Не нужен Docker, браузер, Ollama, GPU.
- **Host smoke (HTTP + DOCX):** на запущенной ACHEWIW Studio через приватное API создаётся искусственный DOCX, проверяются изменения и результаты экспорта, затем **удаляется только созданный тестовый черновик**. Реальные книги пользователя не должны участвовать.
- **GitHub Actions:** повторяет синтаксические и unit-проверки в отдельном CI окружении до установки, уменьшая число бессмысленных пересборок Huananzhi.
- **Ручная браузерная приёмка:** проверка настоящего UI, F5, Undo, открытия SVG/JSON и принятия/отклонения кандидатов. Ни Node unit, ни прежние 27 host-smoke **не заменяют** её.
- **Точность Vision:** отдельное сравнение результата локальной модели с размеченным эталоном. Не покрыта одним только успешным запуском модели.

## 3. Что означают ровно 27 проверок host smoke

Файл: `scripts/docwork-image-host-smoke.py`. Изолированно создаёт синтетический DOCX и рисунок, через HTTP тестирует локальную ACHEWIW Studio (`127.0.0.1:7080`) и закрывает **только свой** тестовый черновик. Счётчик `checks=27` выводится в конце успешного завершения.

Из последнего предоставленного журнала список проверок (в порядке выполнения):

1. Studio health HTTP 200 — приложение отвечает.
2. R3.1 synthetic draft created — тестовый черновик действительно создан.
3. R3.1 editable picture inventoried — найдено изображение, пригодное для правки.
4. R3.1 private thumbnail PNG — миниатюра действительно PNG.
5. R3.1 thumbnail requires token — чтение без токена запрещено.
6. R3.1 image styling saved — настройки оформления сохранены.
7. R3.1 image style survives reload — оформление переживает повторное чтение.
8. R3.2 picture position survives reload — позиция изображения сохранилась.
9. R3.3 paragraph alignment survives reload — выравнивание абзаца сохранилось.
10. R3.1 styled DOCX exported — DOCX реально собран с настройками.
11. R3.2 picture actually moved before chapter heading — позиция картинки в экспортированном документе проверена.
12. R3.2 caption moved together with picture — подпись переместилась вместе с картинкой.
13. R3.2 text edited on document canvas is exported — изменение текста попало в экспорт.
14. R3.3 justified paragraph is real DOCX formatting — выравнивание присутствует в структуре Word.
15. R3.1 actual rounded transparent PNG — сгенерирован прозрачный PNG со скруглением.
16. R3.1 relative width and center alignment — ширина и центрирование применены.
17. R3.5 SVG contains real vector paths without embedded raster — экспорт содержит векторные контуры, а не замаскированное растровое изображение.
18. R3.5 SVG-to-PNG is returned as genuine raster — конвертер отдаёт действительный PNG.
19. R3.6 external artwork upload HTTP 201 — загрузка внешнего изображения прошла.
20. R3.6 artwork denied without secret token — защищённый ассет не выдаётся постороннему запросу.
21. R3.6 private replacement PNG fetched — замену можно получить по разрешённому запросу.
22. R3.6 immutable artwork selection saved in SQLite — ссылка на принятую версию сохранена.
23. R3.6 artwork selection survives reload — выбор версии сохранился.
24. R3.6 new DOCX actually exports accepted artwork — экспорт действительно использует принятую картинку.
25. R3.6 new image remains proportional and rounded — оформление принятой картинки сохраняется.
26. R3.1 source still byte-identical — SHA/байты исходного документа не изменились.
27. R3.1 disposable draft explicitly closed — тестовый черновик удалён по явной команде.

Это **регрессионная защита уже работающих операций**, а не 27 отдельных тестов современного Vision. При неудаче проверки скрипт завершает работу ошибкой: сначала установить причину, затем исправить её; не подавлять тест ради «зелёного» вывода.

## 4. Unit-тесты R3.7/R3.8 и почему они независимы

`tests/diagram-graph.test.cjs`: геометрический граф и ручное подтверждение — кандидаты, неоднозначные связи, подписи, ошибки ID.

`tests/diagram-import.test.cjs`: границы доверия при загрузке ручного JSON — валидный format/version, тот же черновик и рисунок, размеры холста, типы, лимиты, ссылки на реальные объекты.

`tests/vision-proposals.test.cjs`: внешний/модельный JSON по умолчанию **непроверен**; исключить autoApply, чужую картинку, неверные фигуры и оценки; переводить в ручной слой только после действия пользователя.

`tests/test_docwork_vision.py`: детерминированный парсер ответа Ollama и инструкции модели; допустимые блоки, надписи и стрелки, markdown-ограждения, переполнение чисел, мусорный ответ; отдельно проверяется запрет второго GPU-lease внутри ACHEWIW.

Все эти тесты **не запускают реальную Ollama и не измеряют качество распознавания**. Тест GPU-lease тоже не доказывает, что чужие приложения на хосте не используют RTX 3060.

**Не суммировать PASS из всех предыдущих прогонов** как новые уникальные тесты. 63 не означает 63 распознанных рисунка или полную приёмку R3.8.

### Что заметили в последнем журнале и чему это учит

`python3 -m py_compile app/main.py` выдал `SyntaxWarning: 'str' object is not callable` на строке 416. В редакторской задаче для нескольких типов книг строковый литерал следовал непосредственно перед скобкой с тернарным выражением **без оператора `+`**. Python принял синтаксис, но при выполнении этой ветки мог вызвать строку как функцию и выдать TypeError. Исправление: явная конкатенация. Важно: **зелёный синтаксис-тест не равен покрытию рантайм-пути**; создан отдельный регрессионный тест этой ошибки.

В вставленном тексте команды виден повреждённый фрагмент `fi ... pyython`; при этом журнал содержит 27/27 `PASS`, поэтому нельзя достоверно заключить по одному отображению буфера, каким именно был введённый терминальный текст. Факт успешного выполнения smoke подтверждён его собственным итоговым сообщением.

## 6. Новый порядок тестирования — без бесконечных повторов Docker

**Гейт 1 — перед PR:** один раз запускаются `py_compile`, `node --check`, весь Node unit, Python unit и специальный регрессионный тест редакторского отчёта. Затем результаты отправляются в GitHub Actions.

**Гейт 2 — перед обновлением хоста:** GitHub Actions должны быть зелёными. В ходе разработки мелкие исправления не развёртываем на рабочем сервере. Если провалилась проверка, меняем код в ветке и повторяем CI.

**Гейт 3 — одна сборка:** после готовности функционального этапа Huananzhi переключает чистое дерево на конкретную ветку/коммит, исполняет unit-тесты, один `rebuild`, один `auth-check`, один DOCWORK host smoke. Сохраняются commit SHA, название Docker image, вывод тестов и результат HTTP.

**Гейт 4 — браузерная приёмка:** один небольшой **синтетический** DOCX с картинкой. Проверить R3.7: связь/надпись, импорт/экспорт JSON, SVG, Undo, F5; R3.8: наличие реально установленной модели, запуск одного изображения, проверка предложений, поштучное принятие/отказ. Проверить, что оригинальный DOCX имеет прежний SHA и остальные книги не изменились.

**Гейт 5 — качество Vision:** на наборе эталонных технических схем фиксировать точность чтения текста (CER/WER), совпадения объектов по координатам (IoU), полноту обнаружения блоков/стрелок, ложные связи, время выполнения, максимальную VRAM. Пока эти цифры **не измерены**, не писать «полноценное распознавание готово».

## 7. Ориентиры для следующих разработчиков / ИИ-агентов

- Не увеличивать счётчик тестов ради красивого отчёта.
- Новая проверка должна ловить **конкретную регрессию или ошибку**, которую имеющиеся тесты не ловят.
- Тест «модель вернула JSON» не доказывает, что пользователь получил правдоподобный рисунок.
- Различать `syntax PASS`, `unit PASS`, `host smoke PASS`, `browser PASS`, `accuracy benchmark PASS`.
- Не подключать GPU из фоновой задачи без явного действия автора.
- Не удалять чужие файлы, черновики, контейнеры и службы; не пересоздавать SQLite.
- Не объединять все экспериментальные ветки напрямую с `main` без ревью и изолированной проверки.
- При ошибках проверять именно причинный путь, а не бездумно переустанавливать Ollama или Docker.

**Принцип:** тесты существуют, чтобы не потерять уже работающие функции и доказать нужный новый результат — а не для бесконечного цикла «пересборка → 27 PASS».
