# ADR-0003: единая SQLite для канона, RAG, графа причин и редакторского контроля

Статус: **принято как архитектурное направление, не как завершённая реализация**.
Дата: 2026-11-05.

## Решение

Оставить единую SQLite как authoritative source of truth ACHEWIW. Не добавлять PostgreSQL, Neo4j, Qdrant или отдельные контейнеры до измеренного ограничения масштаба, конкуренции писателей, векторного retrieval или графовых обходов. Изменения выполнять аддитивными versioned migrations с резервной копией; изоляция по `project_id`, `branch_id`, `canon_revision` и `job_id`.

**Важно:** RAG — метод извлечения, граф — модель точных отношений. Сами по себе они не являются интеллектуальным редактором. Нужна машина состояний персонажей/предметов/знаний, типизированные доказательства, ретривер и контроллер проверки каждого фрагмента.

## Существующая реализация

- `story_nodes`, `story_edges`, `story_branches`, `story_chunks`, `story_chunks_fts` в `app/story_memory.py`.
- `ai_book_chapters` — отдельные черновики с SQLite checkpoints.
- `projects.data` — исходные карточки/каркас в JSON; одобрение автором отдельное.
- `author_text_revisions` — ревизии уже принятого текста.
- Ollama работает на хосте, Studio в одном управляемом контейнере.
- FTS5 — лексическое извлечение. Нет встроенного embedding index. Отдельная graph DB не требуется для нынешних объёмов.

## Следующие таблицы / расширения — по фазам, не как безусловная автоматическая истина

### P1. Доказуемый канон и происхождение утверждений

`canon_revisions(id, project_id, branch_id, parent_revision_id, author_approved_at, created_at)`

`story_claims(id, project_id, branch_id, kind, subject_id, predicate, object_id, value_json, world_time_start, world_time_end, introduced_scene_id, status, confidence, source_revision_id, source_chunk_id)`

`story_claim_evidence(claim_id, scene_id, paragraph_id, text_span_start, text_span_end, evidence_kind, source_job_id)`

`story_proposals(id, project_id, job_id, scene_id, type, proposed_json, status, reviewed_at)`

**Правило:** LLM может создавать только `story_proposals`; канон меняется в одной транзакции только после авторского подтверждения. Типы статусов: `proposed`, `approved`, `rejected`, `superseded`, `conflicting`. Для доказательств фиксировать hash исходного текста и версии, иначе при правке страницы offsets устареют.

### P2. История как переходы состояний

`story_events(id, project_id, branch_id, event_time_start, event_time_end, narration_order, scene_id, cause_event_id, status)`

`story_state_changes(id, event_id, entity_id, attribute, before_json, after_json, precondition_json)`

`story_knowledge(id, project_id, branch_id, character_id, claim_id, learned_event_id, belief_status)`

`story_mystery_tracks(id, project_id, branch_id, question_claim_id, setup_event_id, payoff_event_id, scheduled_reveal_scene_id, status)`

**Разделить:**
1. время в мире истории;
2. порядок подачи читателю;
3. знания персонажа в момент события;
4. знания читателя к моменту страницы.

Например: герой не может знать тайну, которая раскрывается читателю позже, если в каноне не указан независимый способ узнать её.

### P3. Поиск и контроль продолжения

- FTS5 остаётся первичным retrieval, факты для запросов выбираются SQL по ID и временным интервалам; граф обходится через recursive CTE с ограничением глубины.
- Не полагаться на векторную близость при проверке истинности: она возвращает кандидатов, а не доказательства.
- При необходимости добавить отдельную необязательную embedding table `story_embeddings(chunk_id, model_id, dimension, vector_blob, source_digest)`, использовать host Ollama `nomic-embed-text`. На старте допустим Python cosine ranking для небольшой книги, позже `sqlite-vec` если доступен в образе и измеренно нужен.
- Сборка контекста: `canon_revision` + главная задача + разрешённые знания + граф prerequisites + точные факты + релевантные snippets + последний контекст + запреты на раскрытие.
- После выдачи chunk LLM предлагает структурированные `story_claims` и изменения состояний **как proposals**; детерминированный валидатор проверяет время/предусловия/ссылки и происхождение; LLM-рецензент создаёт гипотезы, не бесшумно меняя утверждённое.
- При коллизии: остановить принятие проблемного chunk либо пометить сомнение и предложить автору исправление; не изменять завершённые главы за спиной автора.

### P4. Ветвление

Copy-on-write branch overlay: дочерняя ветка читает зафиксированный immutable snapshot родителя до `fork_event_id`, а после него — собственные events, claims, states и text revisions. Уникальные stable IDs; запрещено утекание будущих событий из main или соседних branches. Нужны тесты inheritance / fork isolation / rewind / stale canon.

## Индексы и транзакции

- Уникальные/внешние ключи на `(project_id,branch_id,entity_id)` (составные там, где нужны), `PRAGMA foreign_keys=ON`; индексы для времени, статусов и существующих `scene_index`/job scope.
- WAL и `busy_timeout` — только после проверки совместимости с томом/бэкапом. Один сериализованный авторский writer; read snapshots для retrieval.
- Транзакция: принять chunk (или proposal) + evidence + проверка ревизии. Не выполнять сетевые Ollama вызовы внутри открытой транзакции.
- Фоновые embeddings и FTS — воспроизводимые индексы по `digest`, не единственный источник факта.
- Версионированные миграции с dry-run, `integrity_check`, резервной копией и rollback procedure, без удаления рукописей.

## Почему пока не PostgreSQL и не несколько БД

Для локальной книги десятки тысяч слов и даже коллекции романов не требуют отдельного graph server. Переход на PostgreSQL с pgvector имеет смысл при нескольких одновременных авторах, длительных writer-lock, запросах по миллионам фрагментов либо требовании серверного разграничения доступа. Neo4j/Qdrant — только после подтверждённых графовых/vector bottlenecks. С несколькими базами появляются cross-DB consistency, outbox/reconciliation, replay и дополнительные точки отказа.

## Критерии приёмки интеллектуального редактора

1. «Ключ потерян в главе 3 → не может быть в кармане в главе 4 без перехода владения».
2. «Персонаж не знает имя похитителя до соответствующего события».
3. «Читатель может получить намёк, не получая полного раскрытия».
4. «Флешбэк меняет порядок повествования, но не временную причинность».
5. «Предложенная LLM правка не меняет канон без подтверждения автора».
6. «При переписывании абзаца доказательства пересчитываются/помечаются устаревшими».
7. «Ветка what-if не загрязняет main, сохраняет родительскую историю до fork».
8. «Остановленная книга возобновляется с прежнего checkpoint, а не с нуля».
9. «У каждого QA-замечания ID события/факта/фрагмента и уровень уверенности».
10. «Проверки не обещают литературного качества: неоднозначность и авторские художественные исключения допускаются».

**Граница текущего релиза:** этот ADR описывает требуемый следующий слой, но не утверждает, что новые таблицы, временная модель и state-check уже реализованы.

## Уточнение: 1 + 1 SQLite, параллельная проверка и цикл книг (2026-11-05)

**Единственный автор; массовая многопользовательская архитектура не требуется.** Не создавать SQLite по числу пользователей, не дублировать канон в три независимо редактируемые базы. Главный выигрыш от параллельной редакторской проверки даёт пул независимых *читающих* задач и расписание LLM/CPU, а не количество файлов базы данных.

### Рекомендуемые два логических слоя

- **Авторитетная БД** (текущая `DB_PATH`, не переименовывать существующие данные): `projects`, принятые рукописи, `ai_book_chapters`, `author_text_revisions`, утверждения канона, граф причин, хронология, состояния персонажей, сиквелы, авторские решения. Все критичные связные изменения — в одной SQLite транзакции. Утверждение не становится правдой только из-за сходства по embedding.
- **Необязательный index/cache слой**: сначала можно хранить в *той же* SQLite, используя FTS5 и `story_embeddings`. Отдельную `search.sqlite` подключать **только после измерений** чтения/записи или ради изоляции обновления тяжёлого индекса. Там допустимы лишь реконструируемые FTS, векторы, результаты поисковой и предварительной AI-проверки. В кэш обязательно записывать `universe_id`, `book_id`, `edition_id`, `branch_id`, `revision_id`, `source_digest`, `model_id`. Перед показом результата сравнивать ревизию с главной БД; если устарела — не выдавать за текущую, пересчитать.
- **Третья SQLite не нужна**. Опубликованные тома можно хранить как **неизменяемые снимки/экспорты** в архиве и резервных копиях, но это не отдельная рабочая база с конкурирующим каноном.

Многобазовая запись через SQLite `ATTACH` + WAL **не обеспечивает общую атомарность при аварии**. Для derived индекса подходит схема «главная транзакция + записи outbox + индексатор с повторами и проверкой digest»; при сбое индекс перестраивается. Никогда не принимать факт и его связь двумя независимыми записями в разных файлах.

### Параллельная интеллектуальная проверка

Один неизменяемый `revision_id` для всех проверок. На этом снимке параллельно работают:
- SQL/граф: хронология, достижимость причин, зависимости предметов (CPU);
- SQL/машина состояний: арки персонажей, владение вещами, знания/убеждения персонажа (CPU);
- FTS/векторы: поиск предвестников, дубликатов, ранних подсказок и фактических источников (CPU + отдельно запланированная embedding модель);
- LLM-редактор: мотивы, конфликт, читательские ожидания, стилистическая повторы (общий GPU в очереди, не запускать параллельные тяжёлые модели без проверки VRAM).

Сводный результат — `qa_findings` с `checker_id`, `revision_id`, `source_chunk_id`, уверенностью, уровнем нарушения и предложением. Ни одно замечание автоматически не меняет авторский канон.

### Векторный поиск в SQLite

FTS5 — точное лексическое сопоставление, не embeddings. SQLite хранит векторы как BLOB, но сама запись массива не создаёт семантический поиск. Для небольшого корпуса допустим cosine similarity через Python/Numpy по выбранным заранее чанкам; для большего — опциональное расширение `sqlite-vec` или аналог после проверки поддержки в Docker и по результатам бенчмарков. **Не нужен отдельный Qdrant/FAISS сервер по умолчанию**. `nomic-embed-text` доступна через хостовую Ollama; для русского текста сравнить retrieval-качество с мультиязычной моделью вроде `bge-m3` на контрольных вопросах по роману.

Снимки для RAG: `source_type={draft,accepted,published}`, фиксированный `revision_id`, `book_id`, `edition_id`, `branch_id`, `content_hash`. После правки черновика **устаревшие embeddings не должны попадать в контекст**. Чистовик и опубликованный том индексируются отдельными неизменяемыми версиями. Поиск для второго тома по умолчанию видит утверждённый канон и **опубликованную редакцию тома 1**, но не видит отвергнутые черновики, альтернативные ветки или секреты, которых персонаж ещё не знает.

### Многотомный цикл

`universe` (общий мир) → `book` (том) → `edition/revision` (версия) → `scene/chunk`. Сюжетные арки пересекают тома через ID персонажей, состояний, тайн, отношений и обещаний. При публикации замораживается неизменяемый `published_snapshot`; новая книга наследует его канонические факты и состояние мира **на конец первого тома**, а не последнее случайное состояние незавершённого черновика. При конфликте с прежним томом редактор предлагает исправление/осмысленный реткон и просит одобрения автора.

**Это архитектурное уточнение и спецификация**, а не реализация второго файла базы, vector extension или многотомного редактора. Изменять контейнер, мигрировать базу и запускать индексаторы без отдельной проверки/тестов не следует.


## Уточнение: канон без мусора, рабочий overlay, единый RAG+Graph Gateway (2026-11-05)

**Целевая концепция для одного автора.** Автор хочет вынести неудачные ветви, гипотезы и повторно вычисляемые индексы из канонического хранилища, не теряя сохранённых рабочих черновиков и возможности продолжить книгу после перезапуска. Три логические роли могут быть реализованы как три SQLite файла, но это **не обязательное условие производительности** и **не три независимых механизма RAG/Graph**.

### Хранилища и жизненный цикл

| Роль / условное имя | Что содержит | Потери при пересоздании |
| --- | --- | --- |
| `canon.sqlite` (на практике текущая `DB_PATH` до безопасной миграции) | Утверждённый текст и неизменяемые редакции книг, канонические факты, причинный граф, версии состояний, принятые автором решения; manifest опубликованных томов | **Недопустимы** |
| `search.sqlite` (опциональная) | FTS5 и векторные embeddings по source digest, версиям, книгам, томам, branch scope; поисковые индексы, отчёты об извлечении | Допустимо пересоздать по canon + утверждённым рабочим снимкам |
| `work.sqlite` (опциональная, постоянная до явной уборки) | Незавершённые главы, checkpoint генерации, ветки what-if, overlay узлов и рёбер, конкурирующие гипотезы, QA proposals, задания/состояния | **Недопустимы до принятия, отмены или резервирования работы** |

В отличие от оперативного TEMP, `work.sqlite` нужна как durable working set: автор не должен терять 1266 уже написанных слов при перезапуске. Для коротких статистических операций допускаются `TEMP` таблицы и `:memory:` в отдельном соединении. Не следует удалять их служебными скриптами без явного жизненного цикла.

### Нужен один логический RAG и один логический Graph API

`StoryMemoryGateway.resolve(universe_id, book_id, branch_id, revision_id, scene_id, viewpoint_id, reader_state)`:

1. Фиксирует **канонический снимок** (revision/published snapshot). Для what-if — базовую утверждённую ревизию родителя на точке развилки.
2. Достаёт неизменяемые авторитетные рёбра/факты из canon. Применяет только overlay выбранной ветки из work. Нет полного копирования канонического графа на каждую ветку, нет доступа к будущему parent после fork.
3. Выполняет один гибридный retrieval по `search.sqlite` (FTS5 + embeddings) и, при необходимости, по малому индексу текущего рабочего черновика. Результат включает provenance: `source_db`, `source_type`, `source_chunk_id`, `source_hash`, `revision_id`.
4. Отбрасывает чужие branch/tome/edition, отвергнутые предложения, будущие события за пределами временного контекста, сведения вне знаний POV-персонажа. Для авторского omniscient режима разрешено отдельно показывать *секреты для планирования*, но прямо запрещено раскрывать их читателю ранее заданного момента.
5. Возвращает LLM **один компактный пакет**, не raw dump трёх SQLite: правила мира, нужные авторитетные факты, текущие состояния персонажей и арок, незавершённые обещания/setup→payoff, локальный план сцены, краткие цитаты с IDs и последнюю непрерывную прозу.
6. После генерации сохраняет кандидат в work, извлекает новые предложения фактов/состояний, проверяет ссылки/время/противоречия и отправляет автору. Читательская редакция/канон не переписываются автоматически.

**Важно:** физические FTS и векторные индексы могут существовать по обеим сторонам (базовый immutable + маленький writable delta), но `retrieve()` и `graph()` должны оставаться **едиными интерфейсами**, применяющими одни правила приоритета/видимости.

### Отсутствие постоянной полной переиндексации

Стабильные `chunk_id` + `content_hash` + `embedding_model_id` + `revision_id`. При изменении текста в work переиндексировать **только изменённые** фрагменты (delta overlay), а неизменяемый архив предыдущих томов использовать повторно. По принятию автором: создать неизменяемую авторскую ревизию и канонические связи в главной транзакции; записать outbox event; затем асинхронно обновить search index. Если индекс отстал, пометить его stale и до восстановления использовать точные SQL/FTS главной базы, но не подменять старый результат новым каноном.

Кэш/индекс можно чистить по TTL/квотам. История работы (непринятые тексты и принятие/отклонение) должна иметь явную retention policy и безопасные резервные копии. Не удалять все рабочие ветки автоматически.

### Лимит контекстного окна LLM

Чтение трёх баз **не равно загрузке их в LLM**. Планировать по фактическим токенам и реальному `num_ctx`, с резервом под вывод. Пример для 16K: оставить ~3K токенов для следующего фрагмента, а оставшийся вход распределять по задачам; желательно ещё оставить запас на служебные инструкции. Числа динамически подстраивать, а не жёстко обрезать слепым `[:22000]` по символам:

- 0.5–1K правила мира, профиль канона;
- 1–2K план сцены/главы и календарь раскрытий;
- 1–2K соседний/текущий текст;
- 1–3K граф: текущие состояния и причинные ограничения;
- 1–3K проверенные цитаты RAG и релевантные арки/крючки;
- оставшиеся токены — под system/format/вывод.

*Выдавать явные ID/источники, сортировать по важности, не доверять retrieval как доказательству истины.* Не пытаться с помощью большого окна заменить долговременный граф состояний.

### Публикация и сиквелы

`universe_id` → `volume_id` → `edition_id` → `revision_id` → chunks; утверждённый **published_snapshot** неизменяем. Сиквел наследует только утверждённый канон и состояние мира по концовке выбранной опубликованной редакции предыдущего тома. Линии персонажей, долговременные загадки и setup/payoff связываются устойчивыми ID между томами. Отклонённые ветки не становятся «памятью вселенной» по близости embedding.

### Что пока существует, а что только запланировано

**Реализовано:** текущая единственная SQLite, графовые `story_nodes/story_edges`, FTS5 `story_chunks_fts`, раздельная маркировка source draft/approved, индексирование фрагментов, простые branch IDs, контроль части структурных связей.

**Не реализовано:** перенос черновиков в отдельную `work.sqlite`, `search.sqlite` и vector index, base+overlay graph merging, опубликованные межтомные снимки, полноценная state machine и глобальный токен-бюджетный Gateway. Никаких утверждений об ускорении без замеров. Перенос требует проверяемой миграции, восстановления остановленной задачи по существующему job_id, backup/rollback и тестов инвариантов по всем трём файлам.
