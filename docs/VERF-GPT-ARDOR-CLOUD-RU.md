# ACHEWIW — интеллектуальный редактор на Ardor и «Верфь» обучения LLM

**Решение от 2026-11-26. Статус: план / проектирование, НЕ реализовано.** Сохранить основной приоритет — завершить существующий книжный конвейер и редакторский чат. Эта схема дополняет, а не заменяет [промпт 05 «Верфь»](recovery-prompts/05-верфь-обучения.md), [план развёртывания](DEPLOYMENT-ROADMAP-RU.md), [конвейер RTX 3060](CONVEYOR-RTX3060-RU.md) и [опциональный GPT-редактор](OPTIONAL-GPT-EDITORIAL-ORCHESTRATOR-RU.md). Ни один из описанных здесь узлов/провайдеров не следует считать установленным без отдельной проверки.

## 1. Зачем разделять GPT-переговорщика, локальных исполнителей и Верфь

Требование: автор общается с **универсальным интеллектуальным собеседником**, который понимает цель произведения, уточняет только действительно недостающие данные, умеет ставить задачи инструментам и специальным моделям, проверять выполнение, предлагать редакторские исправления и хранить согласованный замысел. Это **не** означает, что каждая генерация абзаца обязана проходить через управляющую LLM: хорошие самостоятельные специализированные LLM также допустимы.

**Три независимых слоя:**

1. **Conversation/Manager (опциональный):** выбранная после тестов сильная instruct/reasoning/tool-use модель; понимает автора, строит версии brief, план главы и задания локальному конвейеру. Важнее измеренное качество понимания, удержание канона и tool-calling, чем слово GPT в имени.
2. **Existing Editorial Conveyor:** текущие Writer → mechanical QA → literary critic → editorial proposals → illustration → proof → author review; Python, SQLite, RAG/StoryGraph и авторский канон остаются источниками истины. Любые изменения текста/канона только с утверждения автора.
3. **Верфь (отдельный необязательный модуль):** готовит датасеты, обучает разрешённые открытые модели (LoRA/QLoRA), ведёт checkpoint/метрики, запускает экзамен, предлагает для установки прошедшие тесты версии. Не блокирует редактуру и не обучается автоматически по любому чату.

Изменение модели-писателя не должно изменять логику редактора, SQLite, форматы документов и источники истины.

## 2. Сетевая и аппаратная схема

```text
Автор в ACHEWIW (браузер Acer)
      |
      v
ACHEWIW Studio / FastAPI / SQLite / RAG     Huananzhi .100, Ubuntu 24.04
      |                                                |
      +--- LOCAL_DIRECT Ollama Writer/Critic/Editor ----+
      |                                                +--- ComfyUI/SDXL
      |
      +--- OPTIONAL MANAGER provider (HTTP over trusted 1G LAN / Cat6)
                              |
                              v
                    Ardor .103, Windows 11 Pro
                    AMD Radeon RX 7600 XT 16 GB
                    selected OpenAI-compatible local API / tool-aware LLM
                              |
                              +-- plans, structured tasks, editorial conversation
                                  (not direct sudo, not autonomous manuscript overwrite)

Верфь на Huananzhi (контроль заданий/хранилище)
      +-- облачные GPU-адаптеры: Kaggle / Colab / Modal / др. после проверки
      +-- Hugging Face: модели, датасеты, версии, разрешённые артефакты
      +-- локальные эксперименты: Huananzhi/Ardor только после проверки training stack
      +-- dashboard loss / lr / steps / VRAM / time / quota / resume / evaluation
```

Ardor — **не GitHub Relay** и не обязательный GitHub-клиент. Для редакции он доступен через LAN от Huananzhi; Git на Ardor нужен только при отдельном clone/pull. Путь ChatGPT ↔ GitHub ↔ Huananzhi/PITOOLS V7 остаётся отдельным каналом разработки/задач; внутренние запросы ACHEWIW к Manager идут напрямую по LAN, без GitHub и VPN. Acer — пользовательский пульт, не обязательный backend. При отсутствии Ardor базовая студия работает на Huananzhi.

**Подбор модели:** оригинальные закрытые GPT-3/GPT-4 локально недоступны; можно испытать открытую gpt-oss и конкурентов. Radeon 16 GB под Windows требует *реальной* проверки inference backend, tool-use, quantization, KV-кэша/контекста и скорости. Наличие Ollama и весов не гарантирует, что весь расчёт на GPU. Проверка QLoRA/ROCm training на Windows для конкретной AMD GPU независима от проверки Vulkan-инференса. Не планировать дообучение на Ardor, пока не доказана совместимость; для экспериментального NVIDIA training возможен Huananzhi и облака, при свободной VRAM.

## 3. Архитектурный контракт Manager ↔ ACHEWIW

Подключить `ManagerProvider` как сменяемый интерфейс и `ConversationRouter`, **без прямого выполнения команд, написанных LLM**. Три режима: `LOCAL_DIRECT` (текущий конвейер, дефолт), `ARDOR_MANAGER` (отдельная LAN модель, опционально), `REMOTE_OPTIONAL` (только явно включённый провайдер с согласием на передачу рукописей и отдельным бюджетом). Не отправлять рукописи в облако без явного выбора автора.

Обмен в структурированном виде: `EditorialIntent` (`project_id`, `draft_version`, `author_goal`, `constraints`, `approved_canon_refs`, `scene_targets`, `proposed_actions`, `evidence_refs`, `questions_if_blocking`). Верификация схемы, ограничения задач, контроль SHA версий, журнал решений, acceptance автора. Новые факты не попадут в канон сами собой.

Сценарии: «написать» → менеджер согласует brief и передаёт специализированному писателю; «редактировать» → указывает строго относящиеся к тексту исправления, сохраняет предыдущую редакцию; «художник» → формирует согласованное описание кадра, но сам не запускает неизвестные команды. Все вкладки видят согласованное задание через существующую SQLite/API модель. При тайм-ауте/отсутствии Manager — явный fallback к LOCAL_DIRECT без потери jobs или рукописей; не подменять молча принятую автором редакцию.

## 4. Верфь: выращивание специализированных моделей

**Порядок:** дефект на реальном произведении → диагностика prompt/канона/RAG/контекста → подтверждённые эталоны и лицензии → train/validation/holdout → LoRA/QLoRA при совместимости → независимый «Экзаменатор» на зафиксированных задачах → публикация версии адаптера после решения владельца.

Виды специализации внутри ACHEWIW: диалог/редакторский бриф, художественный писатель, технический писатель с источниками, литературный критик, корректор/стилист, редактор связности, генератор инструкций художнику. Универсальный Manager **не обязан** дообучаться для всех задач: сначала доказать необходимость адаптации.

**Запись запуска:** `job_id`, `model_id/revision/license`, `dataset_id/revision/license`, `split_hashes`, `base_digest`, `trainer/image/versions`, `LoRA config`, `seed`, `gpu_provider/hardware`, `steps`, `time_budget`, `cost_limit=0 по умолчанию`, `artifact_refs/checksums`, `status`.

**Состояние resume:** вес адаптера, optimizer, scheduler, RNG, global step, training config, ссылки на датасет и основу. Сохранение по периодическим шагам и перед штатным окончанием; внезапный обрыв даёт откат к последнему успешно выгруженному checkpoint. Checkpoint не равен одному LoRA-файлу. Перед переносом между облаками валидировать совместимость CUDA/PyTorch/PEFT/квантования/optimizer; отсутствие совместимости — новый эксперимент, а не ложный «resume».

**Метрики и визуальный экран:** train/validation loss, learning rate, gradient norm (если доступен), steps, tokens/s, GPU/VRAM, время и стоимость; графики наложения сеансов с сохранением глобальной нумерации шагов, отметки pause/resume/checkpoints, реальные квоты (если API позволяет), отдельные метрики экзамена на русских книгах. Снижение loss само по себе **не гарантирует** роста качества текста. «Экзаменатор» сравнивает пары контрольных глав, фактическое удержание канона, диалоги, повторы, редакторские задачи и ссылки, с воспроизводимыми отчётами.

**Изоляция:** Верфь никогда не блокирует основной редактор; GPU аренды совместимы с существующей логикой ACHEWIW; внешние облачные задачи могут продолжаться, когда локальная GPU занята. Не выгружать посторонние модели, не трогать ComfyUI/SQLite и не удалять оригинальные рукописи.

## 5. Провайдеры: что поддерживать по готовности, а не по обещаниям

| Провайдер | Роль | Ограничения/решение |
|---|---|---|
| Kaggle Notebooks | GPU-сессии для LoRA/QLoRA и опытов | Квоты/тип GPU и право доступа меняются; перед запуском спрашивать/считывать доступность; notebook может прерываться |
| Google Colab Free | Отдельный notebook GPU-опыт | Доступность GPU не гарантирована, лимиты динамические; не обходить UX/ограничения автоматизацией |
| Modal | Программный job/инференс/обучение | Платное потребление по тарифам с бесплатными кредитами при наличии; жёсткий budget gate, никогда автоматически не тратить сверх разрешённого |
| Hugging Face Hub | Модели/датасеты/версии/обмен артефактами | Hub удобен для хранения; ZeroGPU Spaces не эквивалент бесплатному произвольному QLoRA trainer; GPU Jobs оплачиваются отдельно |
| Lightning AI | Возможный отдельный кандидат в будущем | Исторический план 05 явно исключает как недоступный; не включать автоматически, заново проверить допуск и бесплатные условия |
| Локальный Huananzhi | Небольшие обучение/тесты на RTX 3060 12 GB | Проверить совместимость модели/контекста/VRAM и свободную аренду |
| Локальный Ardor | Прежде всего Manager-инференс / тесты | Обучение — только после независимой проверки совместимости AMD Windows backend |

Официальная документация на момент оценки (2026-11-26): [Kaggle Notebooks](https://www.kaggle.com/docs/notebooks), [Colab FAQ](https://research.google.com/colaboratory/faq.html), [Modal Pricing](https://modal.com/pricing), [Hugging Face Jobs](https://huggingface.co/docs/hub/jobs-pricing), [HF ZeroGPU](https://huggingface.co/docs/hub/spaces-zerogpu), [Lightning AI Pricing](https://lightning.ai/pricing). Никаких обещаний о фиксированных бесплатных часах или гарантированном сбросе квоты; считывать фактическую доступность при работе. Не включать биллинг и не хранить токены в GitHub.

## 6. Порядок реализации и acceptance (после завершения текущего ACHEWIW)

**A. Стабилизация** существующего создания/редактирования книг, канона, версий, экспорта и связности вкладок; текущая надёжная конфигурация без Ardor.

**B. Ardor Provider — минимальный read-only proof:** инвентаризация установленного runtime, модельный benchmark русского редакторского общения, проверка tool calling, latency, GPU load, LAN timeout и авторизации; локальный REST только по LAN. Никакого GPU обучения пока.

**C. Manager integration:** только две операции plan/review с валидацией схемы, журналом и fallback; A/B baseline vs manager по одним проектам. Расширять роли только после доказанного улучшения.

**D. Верфь MVP:** один тип модели/датасета, один разрешённый провайдер, LoRA train + checkpoint/resume + offline evaluation + экран графиков; export/rollback. Ввести нулевой бюджет по умолчанию.

**E. Мультиоблачная Верфь:** adapters Kaggle/Colab/Modal/HF и локальные тренеры по разрешённым API/UX; обнаружение квот, проверка совместимости переноса, ожидание квоты и возобновление с проверенного checkpoint.

**F. В перспективе:** извлечь универсальную платформу обучения/дистилляции в самостоятельный проект для не-литературных моделей. Не начинать эту работу, пока книжная Верфь не проверена.

## 7. Защита действующей студии

Только отдельные PR/feature flags, тесты SQLite/API, без изменения уже работающего Ollama/ComfyUI/данных, без удаления моделек, без миграций GPU, без установки на Ardor сейчас. Документирование не является внедрением.


## 8. GPT-6 — необязательный внешний эксперт второй линии

**Статус: проектирование, не реализовано.** Локальный менеджер на Ardor и литературный конвейер Huananzhi работают самостоятельно. GPT-6 в ChatGPT привлекается по решению автора при сложностях, повторяющихся дефектах, неудачных тестах, спорных редакторских рекомендациях, деградации после LoRA, диагностике рабочих инструментов и проекта. Не обращаться к облачной модели на каждый абзац.

**Маршрут ручной экспертизы через существующий GitHub:** ACHEWIW/«Верфь» формирует `ExpertReviewBundle` (ID проекта/задания, версия/commit, краткий контекст, описание проблемы, воспроизводимые шаги, короткие разрешённые выдержки, контрольные метрики, результаты локального экзамена, факты и явные вопросы). Huananzhi публикует разрешённые метаданные/ссылки на артефакты в закрытый репозиторий; владелец обращается к ChatGPT, который читает пакет через доступный GitHub-коннектор и предлагает диагностику. Решение проходит верификацию/тесты и отдельное утверждение владельца. Рукописи, лицензионные данные, ключи и личные файлы в GitHub автоматически не публиковать. Публичный репозиторий ACHEWIW не должен содержать закрытый текст рукописей.

**Граница автоматизации:** этот ChatGPT-диалог не принимает постоянные push-сообщения с GitHub и не пробуждается локальным агентом. Для действительно автоматического облачного экспертного запроса потребуется отдельный OpenAI API provider с явным разрешением пользователя, лимитами и учётом стоимости; API-вызов не тождественен продолжению данного чата. При недоступности эксперта ACHEWIW продолжает локальную работу.

**Проверки:** эксперт не должен повышать предложенные авторские факты в канон, применять код, изменять рукопись или запускать платные облачные тренировки без подтверждённого действия. Журнал вопросов, рекомендаций, итоговых тестов и авторских решений нужен для улучшения локального менеджера без автоматического обучения на конфиденциальных текстах.
