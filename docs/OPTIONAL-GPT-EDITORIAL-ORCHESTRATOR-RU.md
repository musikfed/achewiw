# ACHEWIW — нужен ли GPT-посредник над локальными LLM?

**Дата:** 2026-11-26. **Статус:** архитектурное предложение, НЕ интегрировано. Никаких изменений работающих контейнеров, баз данных, системных моделей или GPU-служб.

## Краткое решение
**Локальная LLM может быть самостоятельным собеседником и выполнять литературную работу. GPT-посредник не является обязательным для каждого вызова.** Однако для сложных творческих команд, истории произведения, редактуры канона и организации многошаговых задач полезен **опциональный независимый интеллектуальный собеседник/планировщик**. Выбор поставщика по доказанному качеству, а не по бренду.

Под «GPT от Acer» нельзя подразумевать автоматически сильную локальную модель на самом Acer: Acer может быть пользовательским клиентом. Если GPT-подобная модель работает на Ardor или Huananzhi, доступ к ней можно предоставить ACHEWIW через доверенный LAN API. Реальные возможности и доступность модели сначала проверить. Собственно GPT-3/GPT-4 закрыты для локального запуска; gpt-oss и конкуренты — возможные кандидаты, но не заранее утверждённые победители.

## Что уже есть в ACHEWIW
По README и `docs/CONVEYOR-RTX3060-RU.md`: авторский каркас, возобновляемая генерация глав, SQLite, RAG/StoryGraph, CPU-проверка повторов, литературный критик, редакторские предложения и явное принятие автором, ComfyUI/SDXL, типографский export. Типичный начальный конвейер: Qwen3 8B автор, Qwen3 4B критик/редактор, последовательная аренда VRAM, без тайных скачиваний.

Существующие недостатки качества текста (пустые диалоги, слабая причинность, потеря событий, повторы) не доказывают, что добавление GPT автоматически решит проблему: сначала проверить prompts, канон, retrieval и реальную передачу контекста.

## Предлагаемая схема
```text
Автор в ACHEWIW
   |
   +--> Режим «Прямой локальный LLM» (работает автономно)
   |
   +--> Режим «Умный редактор / переговорщик» [НЕОБЯЗАТЕЛЬНЫЙ]
             |
             +--> понять художественный замысел, жанр, ограничения
             +--> прочитать утверждённый канон и доступную память проекта
             +--> предложить структурированный book brief / scene plan
             +--> задавать только действительно необходимые вопросы
             +--> выбрать задачу локальному писателю/критику/редактору
             +--> проверить фактический результат и причины провалов
             +--> предложить исправления с точными отсылками к тексту
                    |
                    v
         Существующие writer → CPU-QA → critic → editorial proposals
                    |
                    v
          Автор утверждает или отклоняет изменения
```

**Не подменять** канон своим пересказом и не создавать неподтверждённые факты произведения. **Не переписывать главы без решения автора.** Результат планировщика сохраняется как отдельный проверяемый артефакт с ссылками на версии канона.

## Три допустимых back-end режима
1. **LOCAL_DIRECT**: существующий Ollama-конвейер — основная надёжная конфигурация, без стороннего GPT.
2. **LOCAL_MANAGER**: отдельная выбранная по тестам GPT-подобная/сильная instruct-модель на Ardor/Huananzhi через локальный LAN API; GPU-бюджет, очередь и тайм-аут обязательны.
3. **REMOTE_OPTIONAL**: совместимый внешний API при явном подключении и согласии на передачу рукописных данных. По умолчанию отключён, никаких скрытых платных вызовов.

Acer может служить браузерным пультом и наблюдателем; его выключение не должно прерывать текущую локальную работу ACHEWIW. Если выбран provider, зависящий от Acer, UI честно сообщает «поставщик недоступен» и предлагает локальный режим; уже идущая генерация не теряется.

## Этапы интеграции без поломки текущего редактора
1. **Сначала** проверить существующие чаты создания/редактуры, форму редакторского задания и то, как обновления из чата отражаются в остальных вкладках; не дублировать уже готовые функции.
2. Сделать `ConversationRouter` и `PlannerProvider` с конфигурацией `LOCAL_DIRECT` по умолчанию, безопасной отменой, timeout, circuit breaker, без прямого исполнения команд от LLM.
3. Единый типизированный `EditorialIntent`: цель автора, scope проекта/книги/главы, принятые факты, требования, ограничения, ссылки на фрагменты, ожидаемый артефакт, proposed changes, questions и confidence. Валидатор отличает «предложено» от «утверждено».
4. Сохранить принятую автором редакторскую задачу и хеш ревизии в SQLite, не смешивать с сырыми репликами; переносить полезные изменения в связанные вкладки через существующие API, обеспечивать синхронизацию после F5.
5. Инкрементальные тесты «написание» и «редакция»: одинаковые brief, long-context, ошибки канона, диалоги, повторы; измерение фактических improvement, latency, cost, VRAM, rollback.
6. Подключать независимый provider только при доказанном выигрыше; статус provider, политика данных и кнопка fallback в UI. Не менять существующую генерацию/ComfyUI/экспорт до зелёных тестов и ручной приёмки.

## Проверка качества
- Не придумывает факты о героях, событиях, источниках и написанных главах.
- Задаёт уточняющие вопросы только когда невозможен корректный вывод; иначе сам распределяет задачи по вкладкам.
- Главы имеют причинность, внятное введение персонажей, естественные диалоги, развитие события и ритм; не повторяют прежний фрагмент.
- На одну и ту же книгу сравнивать existing baseline vs manager-assisted, blind review по главам, exact author facts и стоимость одного законченного фрагмента.
- Если manager не даёт устойчивого выигрыша, оставить его отключаемым и не усложнять конвейер.

## Сохранение работоспособности
Не удалять/изменять SQLite, рукописи, архивы, существующие Ollama-модели, docker volumes, ComfyUI и другие сервисы. Внедрение — отдельный PR с CI и реальной проверкой на Huananzhi только после явного решения владельца.
