**Не повторяем** 27/27 smoke DOCWORK, 28/28 геометрию, ручной CorelDRAW PowerTRACE (63 curves), Vision HTTP 422/503 и аппаратный probe. Главная цель — **сначала уберечь фактически созданную книгу, затем безопасно продолжить генерацию**.

## Что добавлено в этой ветке

`scripts/backup-book-job.py` — самостоятельный Python 3.12 инструмент без зависимостей кроме стандартной библиотеки. **Он не запускает Ollama, не перезапускает Docker и не изменяет базу источника.** `sqlite3.Connection.backup()` делает согласованную онлайн-копию **всей** ACHEWIW SQLite, включая WAL, если сервис продолжает работать. По выбранному `job_id` считает главы, слова, флаги complete/accepted и сохранённые части потока из `ai_book_stream_buffers`. Тексты не печатаются на экран: находятся внутри сохранённой SQLite. Архив ZIP проверяется CRC и SHA256, оригинальная БД открывается только в read-only.

`--list` ничего не создаёт и возвращает последние задания книг: job_id, project_id, статус, фактические сохранённые слова/главы. Это безопасная команда **для идентификации** книги на 67%. Показатель 67% пока не повторён на настоящей БД.

### Выполнение на Huananzhi (ТОЛЬКО после появления скрипта локально)

Узнать реальный путь БД: сервер `/1tbdisk/achewiw`, сервис обычно в Docker с `ACHEWIW_DATA_DIR=/data` и `DB_PATH=/data/achewiw.sqlite3`. **Сначала выяснить host bind mount**, не угадывать путь. Затем на Linux-хосте, где доступен реальный db-файл:

```bash
# УКАЖИ ФАКТИЧЕСКИЙ host-путь, полученный из docker compose или mount:
DB=/actual/host/path/achewiw.sqlite3
python3 scripts/backup-book-job.py --db "$DB" --list

# Скопируй ID нужной книги из --list. Сохранение В НОВЫЙ файл:
JOB_ID=<actual-job-id>
mkdir -p /safe/private/achewiw-backups
python3 scripts/backup-book-job.py --db "$DB" --job-id "$JOB_ID" \
  --out "/safe/private/achewiw-backups/book-job-${JOB_ID}-20261124.zip"
```

**ВНИМАНИЕ:** SQLite включает рукописи и другие проекты. Архив содержит секреты/личный контент проекта, НИКОГДА не коммитить в GitHub. Для резервного диска проверить место; архив исходную БД не удаляет и по существующему пути не перезаписывает.

## A1.3 — Дополнить проверенную копию SQLite внешними материалами

Добавлен `scripts/archive-book-external.py` — **дополнение нового ZIP**, а не изменение исходной SQLite или уже созданного rescue-архива. Включаются **только явно указанные файлы и папки**; это важно, чтобы не захватывать случайные большие каталоги других проектов или файлы с секретами.

Пример после успешного A1.2 (пути заменить на реальные):

```bash
python3 scripts/archive-book-external.py \
  --source /safe/private/achewiw-backups/book-job-A1.2.zip \
  --out /safe/private/achewiw-backups/book-job-A1.3-external.zip \
  --include workspace=/actual/path/to/work-files \
  --include illustrations=/actual/path/to/book-illustrations
```

Дополнительные папки/файлы `--include` выбирать только после **read-only инвентаризации связей с конкретной книгой**. Если файл CDR/PSD лежит на Acer, архив с Linux-хоста его сам не увидит: копию передавать только явным действием, не изменяя VPN и не перемещая оригинал.

Внутри итогового ZIP появляются `external/<scope>/...` и `report/external-manifest.json` с `sha256` и числом байтов каждого вложения. Повторное имя scope, относительные пути, символические ссылки, странные имена, архив самого себя и перезапись уже существующего результата запрещены. Итоговый SHA256 ZIP рассчитывается **потоково**, без чтения всего ZIP в оперативную память.

**Ограничение:** `publication_snapshot_complete=false` и `coverage_verified=false` сохраняются даже после успеха: скрипт доказывает целостность *переданных* файлов, но не то, что выбраны вообще все части конкретного произведения. Для статуса COMPLETE нужен следующий этап — обязательный перечень зависимостей проекта по реальной БД, серверной файловой системе и материалам Acer.

## A1.4 — Независимая проверка архива, без восстановления поверх рабочих файлов

Код `scripts/verify-book-rescue.py` читает уже собранный ZIP, валидирует SHA256/CRC, делает временную локальную копию SQLite, выполняет `PRAGMA quick_check` и сравнивает фактические главы и буферы с исходным манифестом. При наличии внешних файлов сверяет **каждый** `external/*` по SHA256/размеру; проверяет дубликаты ZIP и traversal. Команда НЕ трогает оригинальную SQLite и рабочую папку проекта.

```bash
# Подставить фактический готовый ZIP A1.3:
python3 scripts/verify-book-rescue.py \
  --archive /safe/private/achewiw-backups/book-job-A1.3-external.zip
```

При успехе `verified: true` означает только: **данные внутри данного архива проверены**, а `publication_snapshot_complete: false` честно означает, что перечень всех внешних зависимостей конкретной книги пока не установлен. Это не разрешение автоматически продолжать генерацию на живой БД до инвентаризации.

НЕТ удалённого SSH-доступа из GitHub-коннектора: локальный Python скрипт сначала должен оказаться на Huananzhi и запускаться владельцем на **реальном пути** SQLite. По этим данным мы уже разберём причину паузы 67% — без повторных генераций.
