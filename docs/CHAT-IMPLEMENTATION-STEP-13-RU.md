# ACHEWIW · Шаг 13 — смысловая подгонка по авторским материалам RAG/Graph

**Статус:** Draft PR. Реализация без развёртывания на сервере и без прямой записи в канон. База — проверенный шаг 12 и издательский эталон «Гантова зебра» r04.

## Сценарий

В уже существующей вкладке **06 · Типография** автор выбирает написанную главу и физический номер страницы PDF-пробы, указывает редакторское поручение и установленную модель Ollama.

1. Система собирает **реальную A5 PDF-пробу**, измеряет заполнение страницы; проверяет, что страница относится к выбранной главе, не начинается следующая часть/глава и нет выраженных растянутых пробелов. Только решение `offer_semantic_expansion` открывает генерацию.
2. Из **существующего** `story_memory.retrieve` запрашиваются фрагменты авторской рукописи/синопсиса и одобренные автором узлы графа по этому же проекту. Непринятые черновики и `outline`-узлы исключаются. Если опоры нет — **409, генерации нет**.
3. В существующей ACHEWIW SQLite GPU-lease резервируется одно `semantic_page_fit`-действие. Сервис не скачивает модель и не создаёт новую очередь. Вызов Ollama ограничен: короткий контекст, один JSON-абзац, до 180 слов.
4. Ответ модели проходит проверку формы JSON, количества слов, ID опорных фрагментов и сильных текстовых повторений. Это **не проверка фактической достоверности**, поэтому даже корректный кандидат нельзя автоматически вставить в книгу.
5. Кандидат и ссылки на авторские материалы сохраняются в **отдельной** таблице `ai_page_fit_suggestions` с SHA исходной главы и снимка проекта; книгу, DOCWORK, сноски, RAG и Graph **не переписывают**.
6. В интерфейсе можно восстановить кандидат после обновления, просмотреть опоры, отклонить его, либо **передать только текст** в существующий read-only PDF предпросмотр шага 12. Он измеряет сдвиги страниц и глав при временной вставке в памяти.
7. Для реального внесения текста автор обязан отдельно проверить исторические/технические факты и воспользоваться прежней редакторской процедурой с версией, сравнением и отдельным подтверждением; прямого endpoint `approve` здесь **нет**.

## Осмысленная подгонка, не заполнитель

- Не заполнять пустые страницы перед новым разделом или главой.
- Не исправлять межсловные пробелы литературной генерацией.
- Никакого «111111…», слов ради счётчика, вымышленных дат, производительности или ссылок.
- При отсутствии надёжного контекста RAG/Graph **не создавать** дополнительный абзац.
- Ссылка на фрагмент **авторской рукописи** означает происхождение утверждения, а не его независимую историческую проверку.
- Проверять сноски и связанные страницы после фактической правки и нового экспорта PDF. Эталон r04 фиксирует 527 PDF-страниц и несовпадение оглавления; это задача типографского preflight, а не повод искусственно увеличить текст.

## Ограничения

- Пока не подключены подтверждённые внешние библиографические источники и автоматизированная факт-проверка — утверждать независимое подтверждение модельных фактов нельзя.
- Модель генерирует кандидат только для **измеренно недозаполненной страницы**, принадлежащей выбранной главе. Измеритель по текущей версии PDF имеет эвристики, поэтому рекомендации требуют редакторского просмотра.
- Не выполняется обновление полей DOCX на сервере Word/LibreOffice; сохранилась проверка конечного PDF и `updateFields` Word из шага 12.
- Нет авто-accept на основе того, что количество страниц стало меньше: важно качество текста.
- Существующий рабочий порт 7080 и DOCWORK не тронуты, отдельный 17080 не создаётся.

## CI

```bash
python -m py_compile app/semantic_page_fit.py app/semantic_page_fit_api.py app/main.py
python -m unittest discover -s tests -p 'test_semantic_page_fit_step13.py' -v
python -m unittest discover -s tests -p 'test_print_proof_step12.py' -v
node --check app/static/chat_studio.js
```

Синтетические тесты используют временную SQLite, имитацию локальной Ollama, авторский RAG, конфликты GPU, устаревшие версии и запрет записи в основной текст. Реальную Ollama и реальную книгу на тестовом сервере они не запускают.
