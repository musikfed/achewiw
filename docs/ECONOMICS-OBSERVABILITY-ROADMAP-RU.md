# ACHEWIW — экономика и эффективность вычислений (проект будущей вкладки)

**Инициатива автора: 24.11.2026. Статус: только спецификация/стратегия.** Ничего не подключать к работающему серверу, GPU, сетевым интерфейсам или конвейеру книг до завершения критичных задач. Основная цель: **сколько затратил ресурсов и насколько быстро получил результат**, а не поток шумных системных датчиков.

## Экономика как отдельная вкладка: простой взгляд автора

Вкладка **«Экономика»** в Studio, с выбором периода (сегодня / 7 дней / 30 дней / произвольно) и проекта (все / конкретная книга / комикс). На верхнем уровне **шесть основных цифр** с указанием достоверности:

1. **Токены: вход + выход + сумма** — реальные usage модели, накопительно; отдельно по провайдеру/модели и произведению, если есть достоверный job context.
2. **Отклики системы:** типичное (p50) и медленное (p95) время ответа, скорость генерации **выходных токенов/секунду**; количество завершённых задач и ошибок/таймаутов.
3. **Электроэнергия сервера:** общий расход кВт·ч и рубли по заданному тарифу; отдельно **доля GPU** (кВт·ч), но не складывать её с общим расходом сервера повторно.
4. **Сеть:** принятый RX, отправленный TX и RX+TX за период; указываем интерфейс/область измерения (WAN, VPN, LAN), не называем суммарный трафик всех интерфейсов интернет-трафиком.
5. **Облачные расходы:** фактические billed tokens / списания / квоты, где доступны; иначе честное «неизвестно/оценка», не придумывать цену.
6. **Себестоимость проекта:** доступные затраты (электричество и внешние API) на книгу/комикс, объём созданного/принятого текста и стоимость полезного результата. Не считать токены локальной Ollama денежной оплатой API: вычисления локальны, стоимость — амортизация/электричество, если учтены.

На втором уровне: **один основной график потребления за время** с переключателем «токены / кВт·ч / ₽ / трафик / задержка»; фильтры модели, провайдера, типа операции и проекта. Сумма, детализация по наведению/таблице. Экспорт CSV/JSON по явной команде.

## Какие данные собирать и как

### 1. Единая бухгалтерия LLM-запросов

Одна запись **на каждый реальный вызов** модели через общий instrumented adapter, включая генератор, DOCWORK, локальную редактуру, Vision, RAG/Graph, Codex-подобные задачи, облачные LoRA/дистилляцию и будущую Верфь. Для конвейеров с несколькими вызовами — отдельные дочерние usage events, объединяемые `operation_id`; повторные попытки тоже имеют собственную стоимость, но не считаются дополнительным успешно принятым результатом.

Поля: `time_utc, request_id, operation_id, project_id? , model_id, provider, source_component, status, input_tokens, output_tokens, total_tokens, usage_source, duration_ms, time_to_first_token_ms?, eval_tokens_per_s?, cost_currency?, billed_amount?, error_class?`.

**Приоритет точности:** реальные `prompt_eval_count` / `eval_count` и `prompt_eval_duration` / `eval_duration` от Ollama; provider usage для облачных API; собственный tokenizer только в режиме `estimated`, строго с указанием модели/токенизатора. У мультимодальных моделей отдельные поля `image_count, audio_seconds?`, т.к. токены и стоимость могут не совпадать с простым подсчётом текста. Если провайдер не сообщает использование — **«нет данных»**, а не 0.

**Нельзя измерять дважды:** при работе через агентский прокси usage логировать у того слоя, который действительно знает billable counts. Не записывать всю строку промпта, сгенерированные главы, авторские тексты, API-ключи или личные данные; только агрегаты + безопасные IDs. Делать append-only usage ledger, индексы по времени/модели/проекту и агрегаты в час/день. Учёт входных и выходных данных по всем моделям без исключений для будущих *поддерживаемых* адаптеров; неизвестные адаптеры отмечать как `unmetered`.

### 2. Электроэнергия — реальные данные там, где доступны, иначе оценка

- **GPU NVIDIA RTX 3060:** опрос `nvidia-smi --query-gpu=power.draw,utilization.gpu,memory.used` с небольшим, ограниченным интервалом (например, 15–60 с). При дискретной выборке интегрировать ватт × интервал в Вт·ч, при сбое показаний маркировать пробелы. `power.draw` — моментальная потребляемая мощность GPU (в границах датчика), **не общая потребляемая мощность компьютера**. Вычислять долю GPU только при занятом графическом устройстве или общую по GPU с явным названием методики.
- **CPU/сервер:** если на данной платформе доступны надёжные RAPL/hwmon-счётчики, читать проверенные источники; если датчика нет — оценка по выбранной модели мощности и времени активности, явно **«оценка»**. На двух старых Xeon RAPL не гарантирован. Для точного учёта **общего расхода сервера из розетки** нужен внешний ваттметр/умная розетка с измерением. Без него нельзя показывать придуманные кВт·ч как точные.
- **Правило суммирования:** если известна `server_total_kwh` из внешнего измерителя, **GPU energy является частью этой суммы**, отдельная карточка для объяснения и не плюсовать повторно. Если общего измерителя нет — оценка `server_estimated_kwh` по модели с широким допуском и отдельная GPU telemetry.
- Тариф руб/кВт·ч вводит пользователь. По умолчанию «не задан», никаких догадок о месте и тарифах. Фоновая работа других сервисов учитывается: нельзя приписывать всё потребление книги.

### 3. Сеть: входящий, исходящий и суммарный трафик

- Linux `/sys/class/net/*/statistics/rx_bytes`, `tx_bytes` или `/proc/net/dev` c интервалом 60 сек или реже; по выбранному физическому WAN интерфейсу. Разница счётчиков; перезагрузка/сброс счётчика = отдельная эпоха. Для VPN-туннеля выводить **отдельную** цифру: сумма по всем интерфейсам ведёт к двойному счёту.
- **Важно:** RX/TX физического интерфейса — это трафик сервера, а не чистый «интернет»; LAN может доминировать. По умолчанию назвать «сетевой трафик сервера», а «Интернет» только при доказанной границе WAN. Без packet inspection и хранения payload.
- Измерение скорости передачи: байт/с по разнице счётчиков в выбранном окне, не путать с latency API.

### 4. Скорость и полезность работы

- Для каждой операции: очередь/ожидание, время до начала, общая длительность, успех, ошибка, повтор, отмена, сколько токенов выдано, `tokens/sec` на время декодирования по метрике провайдера. В UI верхний уровень — p50/p95 latency и процент успеха, без графиков для каждого системного вызова.
- Отдельные показатели конвейера: **минут/глава, завершённых глав/проект, процент успешно принятых результатов, время экспорта DOCX/PDF**, при наличии экономического смысла. Для long-running операций latency и токенизацию показывать по операции, не только по HTTP.
- Кэшированные действия и ручные операции без LLM: input/output tokens = «не применимо», **не выдавать за нулевой вызов модели**.

## Перфоманс и безопасность внедрения

- Нет отдельного LLM/ИИ для сбора метрик и никаких дорогостоящих запросов для расчёта. Счётчики и usage — побочный эффект уже выполненного действия; минимальные системные опросы в фоне в **одном** worker и предагрегация раз в час/день.
- Один репозиторий схемы, без дублирующих подсчётов между страницами. Лимиты хранения и retention согласовать с автором; никакого автоудаления действующих проектов и снимков. Если метрика недоступна — приложение продолжает работать и показывает пробел.
- SQLite для первых версий; экономическая вкладка **read-only** относительно книги, не блокирует генерацию/редактуру на 67%. Хранить период/время, модель и счётчики; не промпты/тексты. Уменьшить частоту опроса, когда сервер простаивает.
- Исходящий трафик клиентских устройств, энергию мониторов/роутера и облачных VM не включать в «сервер» без отдельного источника.
- При коммерческой эволюции: метрики по tenant/workspace и выставленные счета на основе поставщика API, quotas/budgets, справедливое распределение затрат пула, роли доступа к расходам, экспорт и аудит.

## Порядок реализации после основного конвейера

**Сейчас — только зафиксировать требования и места интеграции.** До выполнения P0: целостные snapshot книги с 67% и generator chapters, стабильная генерация, DOCWORK с подготовкой DOCX/PDF, Graphics Bridge и возврат картинки по image_index. Преждевременно не создавать отдельный dashboard с фиктивными данными.

**R1 (первый минимальный полезный этап):** токены Ollama input/output и длительность для существующих реальных вызовов в едином лёгком ledger; пара фильтров и график накопления. Дополнить временем задач (p50/p95) и базовыми сетевыми счётчиками RX/TX.
**R2:** доступная GPU power telemetry, безопасная интеграция кВт·ч; конфиг тарифа, отдельная модель оценки полного сервера / внешний ваттметр.
**R3:** облачные API и токены/денежные лимиты, себестоимость проекта и Верфь.
**R4:** мультипользовательская экономика и resource accounting для общего GPU-пула.

## Критерии готовности

- [ ] При каждом тестовом LLM-вызове есть единая запись с реальными input/output counts или явной пометкой unknown/estimated; нельзя удвоить при retry/proxy.
- [ ] «Сегодня / 7 дней / месяц / проект» суммы сходятся с низкоуровневым ledger.
- [ ] Отклик p50/p95 и throughput не включают idle timestamps и несопоставимые длительности.
- [ ] Серверные кВт·ч без внешнего ваттметра **помечены оценкой**, GPU кВт·ч не сложены второй раз.
- [ ] RX/TX по одному физическому интерфейсу и VPN отображаются без двойного счёта.
- [ ] Пользователь одним взглядом видит расход за период и динамику, при этом no-data корректно отображаются как no-data, а не 0.
- [ ] Нагрузочный benchmark показывает, что сбор метрик не вносит существенного overhead; отсутствие GPU/сетевого датчика не ломает редактуру.
