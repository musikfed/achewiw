# ACHEWIW · R2 — сохранность иллюстраций и их подписей

**Дата:** 23.11.2026. **Статус:** реализация в отдельном draft PR [№25](https://github.com/musikfed/achewiw/pull/25), не установлена на сервере.  
**База изменений:** R1 (draft PR №24) → R2; всё внутри одного ACHEWIW, без самостоятельного приложения.  

## 1. Исправленные причины потерь

1. **Иллюстрация не найдена:** раньше `illustrations_core.asset_for_export()` пропускал запись из SQLite, если PNG отсутствовал, являлся ссылкой или превышал лимит. Результат мог выглядеть как успешная книга без рисунка. **Теперь это явный отказ** с ID иллюстрации. Запись и исходный файл не удаляются.
2. **Повреждение PNG:** `book_layout_core.verified_illustrations()` проверяет путь, размер, формат и доступность PNG, обнаруживает дубликаты ID. Проверка одна для DOCX, PDF, FB2 и EPUB, включая прямое использование функций генерации. Никаких изменений живой базы.
3. **Разрыв рисунка и подписи:** DOCX использует `keep_with_next` для абзаца рисунка и `keep_together` для подписи. Портретные изображения ограничены по высоте (12 см) для A5.
4. **PDF A5:** ReportLab использует `KeepTogether([Image, Caption])`; высота подписи измеряется заранее и резервируется в геометрии кадра. Блок переносится целиком на следующую страницу, если не помещается в текущей.
5. **EPUB:** изображение и подпись оформлены как `<figure><img .../><figcaption>...</figcaption></figure>` с `break-inside:avoid`. Некоторые читалки могут игнорировать это свойство: абсолютной гарантии пагинации EPUB **нет**.
6. **FB2:** исходный PNG и подпись сохраняются в книге, но точная пагинация определяется читалкой.

## 2. Что проверяет изолированный тестовый набор

`tests/test_r2_illustration_fidelity.py`:

- DOCX — соседство рисунка/подписи, свойства Word против разрыва, предельный размер высокого PNG;
- PDF — расположение рисунка и подписи **на одной и той же странице** при нескольких границах страницы, в том числе у портретного рисунка и длинной подписи; анализ через PyMuPDF;
- EPUB/FB2 — наличие PNG в контейнере и подписи, XHTML figure/figcaption;
- для каждого формата — отказ при отсутствии файла или повреждении, сохранение записи о проблемном изображении;
- HTTP API — код 409 и точный ID отсутствующего файла; никаких автоудалений и «тихого успеха».

### Команда (только в изолированной тестовой среде)

```bash
PYTHONPATH=app python3 -m pytest -q tests/test_r2_illustration_fidelity.py
```

В GitHub Actions новые тесты выполняются **после установки шрифтов DejaVu**, совместно с издательским тестовым набором. Реальные рукописи не используются.

## 3. Что ещё НЕ гарантируется

- Визуальная идентичность DOCX между MS Word и LibreOffice. Word использует `keep_with_next`, но результат необходимо просмотреть перед печатью.
- Любые большие плавающие объекты, таблицы со сложными ячейками, сноски, полиграфический PDF/X.
- Перенос всех особенностей исходного PDF → DOCX остаётся ограничен возможностями R1.
- Сквозное нормативное соответствие ГОСТ и качество библиографии.
- Издательская модерация, подписи/лицензии сторонних авторов и автоматическая публикация.
- Не проводится обновление `main`, сервера, Docker, SQLite или других проектов.

## 4. Порядок дальнейшей работы

- R2 считается готовым на уровне **искусственных тестов и успешного CI** только после завершения проверки последнего коммита ветки;
- затем R3: сохранение настроек, правок и редакторской сессии после F5;
- далее R4: нормативные стили, библиография, редакторские профили и ручная приёмка.

Реестр этапа 00-Д остаётся **BLOCKED** до полного испытания и одобрения реального издательского продукта. Это не сертификат ГОСТ и не автоматический допуск к публикации.
