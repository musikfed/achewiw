# Сквозная имитация ACHEWIW · шаги 11–14 — 25.11.2026

**Цель:** проверить одну связанную историю создания книги вместо изолированных unit-тестов.

**Результат:** PASS. GitHub Actions workflow [#45642408090](https://github.com/musikfed/achewiw/actions/runs/45642408090), 2 сквозных теста и **33 регрессионных теста** (9+7+9+8), всего 35 PASS. Окружение: Ubuntu runner, Python 3.12, временная SQLite, настоящий ReportLab/PyMuPDF, DejaVu, `httpx.MockTransport` для Ollama. Никаких запросов к домашнему GPU.

## Фактические метрики трёхглавой синтетической книги

| Состояние | Физических страниц PDF A5 | TOC: фактическое начало 1 / 2 / 3 |
|---|---:|---|
| До вставки | **9** | 3 / 5 / 7 |
| После принятой вставки во 2 главу | **10** | 3 / 5 / 8 |
| После защищённого отката | **9** | 3 / 5 / 7 |

Все шесть значений оглавления **извлечены из реально экспортированных PDF**, сравнены с фактическими страницами заголовков и совпали. PDF после вставки действительно меняется, новая глава 3 сдвигается на страницу 8, откат возвращает её на страницу 7. Контрольные тексты глав 1 и 3 остались без изменений.

## Испытанный сквозной маршрут

1. Пустой проект → три утверждённые главы и распределение 2100 плановых слов (`chat_outline_builder`, шаг 11).
2. Наполнение синтетическими техническими текстами → настоящий A5 PDF с кликабельным TOC и обновляемое XML-поле Word TOC в DOCX (`publishing_exports`, шаг 12).
3. Проверенный авторский фрагмент → JSON-предложение редакторского абзаца от **имитированной** Ollama, ссылки на evidence ID обязательны, неутверждённый черновик исключён (`semantic_page_fit`, шаг 13).
4. Проверка предпросмотра PDF до/после и отсутствие изменений рукописи до подтверждения. Подтверждение источников и пагинации → атомарное принятие в SQLite, повторное создание настоящего PDF и его preflight → CAS-откат и проверка исходных текстов (`page_fit_editorial_api`, шаг 14).
5. Негативный тест: намеренный разрыв части и подозрительная выключка по ширине не должны запускать «добивку» текстом.

## Найденный и исправленный дефект

До E2E `print_proof_preflight.NUM_RE` распознавал лидеры-точки, но не **широкие пробелы**, реально используемые ReportLab `TableOfContents`. В результате главы обнаруживались (3, 7, 11 в первой слишком длинной фикстуре), однако `toc_page` оставался `null`.

После исправления разбор учитывает последовательности из двух и более пробелов/табуляций **в дополнение к** лидерам-точкам, а проверка требует совпадения номера с физической страницей. Это изменение остаётся в зависимой тестовой ветке до принятия PR.

## Ограничения / следующий шаг №15

- Настоящая Ollama, реальный веб-интерфейс `7080` и рабочие базы не задействованы.
- GitHub Actions не доказывает, что Word полностью пересчитал TOC после форматирования, поскольку DOCX содержит поле `TOC` с `updateFields`, а не автоматический headless Word-layout на сервере.
- Редакторское подтверждение в E2E **имитировано** через TestClient, не было реального человека, проверяющего технические факты.
- До выпуска нужен **печатный release gate**: пересчёт полей DOCX в офисном движке, повторный PDF, автоматическая сверка видимых номеров / ссылок / физической нумерации, блокировка публикации при ошибках.
- Визуальная ручная инспекция каждой полосы PDF не заменяется машинными тестами. Скачиваемые тестовые PDF оставлены как просмотрные артефакты.

Код и тесты в Draft PR #79; `main`, DOCWORK, рабочий `7080`, авторские рукописи, модельный сервер и порт `17080` не менялись.
